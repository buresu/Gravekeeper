# Configuration

Gravekeeper stores its settings in a TOML file. The GUI edits it for you, but it can also be edited by hand; use **Settings → Reload** (or restart Gravekeeper) afterwards.

## Locations

| OS | Configuration file | Data (history, logs, backups, lock file) |
|---|---|---|
| Linux | `~/.config/gravekeeper/config.toml` | `~/.local/share/gravekeeper/` |
| macOS | `~/Library/Application Support/Gravekeeper/config.toml` | `~/Library/Application Support/Gravekeeper/` |
| Windows | `%APPDATA%\Gravekeeper\config\config.toml` | `%APPDATA%\Gravekeeper\data\` |

`$XDG_CONFIG_HOME` and `$XDG_DATA_HOME` are honored on Linux. The window size and the selected tab are saved separately by the GUI toolkit (eframe) in `app.ron` in its own data directory (on Linux, `~/.local/share/gravekeeper/` as well).

Setting `GRAVEKEEPER_HOME=<dir>` puts everything (config, history, logs, lock file) in `<dir>` instead, which is useful for portable installs and testing.

Inside the data directory:

| Path | Contents |
|---|---|
| `history.sqlite3` | Event history and the last run time of each schedule |
| `logs/<app-id>.log` | Output of each application (if enabled), with timestamps; `out`, `err` or `---` (lifecycle note) after the time |
| `logs/schedule-<id>.log` | Output of a schedule's `run` actions |
| `logs/gravekeeper.log` | Gravekeeper's own log (10 MiB, 5 old files kept) |
| `backups/config-<time>.toml` | The configuration as it was before each save (newest 20 kept) |
| `gravekeeper.lock` | Ensures a single instance |

On Unix the configuration and log files are created with mode `0600` and their directories with `0700`. Every save is atomic (written to a temporary file, then renamed); the previous version is kept as `config.toml.bak` and as a timestamped copy in `backups/`.

## Example

```toml
schema_version = 2

[general]
start_minimized = true   # open only the tray icon at startup
log_lines = 5000         # stdout/stderr lines kept in memory per application

[monitoring]
enabled = true
interval = 5        # seconds between samples
cpu_alert = 0       # percent; 0 turns an alert off
memory_alert = 90
disk_alert = 90     # applies to every listed disk
sustain = 60        # must stay at or above the threshold this long

[logging]
app_log_files = true   # also write application output to files
max_file_mb = 10       # rotate beyond this size
keep_files = 5         # rotated files kept (.1 is the newest)

# Applications start automatically in this order, top to bottom.
[[app]]
id = "web"                       # stable identifier; generated by the GUI
name = "Web server"
program = "/usr/local/bin/web"   # run directly, never through a shell
args = ["--port", "8080"]
cwd = "/srv/web"                 # optional
autostart = true                 # start when Gravekeeper starts
start_delay = 10                 # seconds to wait after Gravekeeper starts
boot_delay = 120                 # and until the computer has been up this long
startup_grace = 3                # must stay up this long to count as started
stop_timeout = 15                # seconds between the stop request and a forced kill

[app.env]
RUST_LOG = "info"

[app.restart]
mode = "on-failure"   # "on-failure" | "always" | "never"
backoff_initial = 1   # seconds; doubled after each consecutive failure
backoff_max = 60
max_restarts = 5      # give up after more than this many restarts...
window = 300          # ...within this many seconds
stable_after = 60     # running this long resets the failure count

[[schedule]]
id = "nightly"
name = "Nightly restart"
when = { kind = "weekly", days = ["mon", "thu"], time = "03:00" }
action = { kind = "restart", app = "web" }
missed = "run-once"        # "skip" (default) | "run-once"
time_zone = "Asia/Tokyo"   # optional; the system time zone by default

[[schedule]]
id = "cleanup"
name = "Clean temporary files"
when = { kind = "interval", every = 3600 }
action = { kind = "run", program = "/usr/local/bin/cleanup", args = ["--all"], timeout = 600 }

[[webhook]]
id = "ops"
name = "Ops channel"
url = "https://hooks.slack.com/services/…"
format = "slack"           # "json" (default) | "slack" | "discord"
events = ["app_exited", "restart_gave_up", "schedule_failed", "resource_alert"]
apps = []                  # only these application ids; empty means all
[webhook.headers]          # optional extra request headers
Authorization = "Bearer …"
```

All durations are whole seconds. Every field of an `[[app]]` except `id`, `name` and `program` is optional and defaults to the values shown above (`enabled = true`, `autostart = false`, `start_delay = 0`, `boot_delay = 0`, `startup_grace = 1`, `stop_timeout = 10`).

To run something through a shell, say so explicitly:

```toml
program = "/bin/sh"
args = ["-c", "exec my-tool --flag | tee -a /tmp/out.log"]
```

## Automatic start order

Applications with `autostart = true` start in the order they are listed. Each one waits for its own `start_delay` (counted from when Gravekeeper started) and `boot_delay` (counted from when the computer started), and never starts before the ones above it. Use the ⬆/⬇ buttons in the GUI to reorder.

## Schedules

`when` is one of:

| `kind` | Fields | Runs |
|---|---|---|
| `once` | `at = "2026-12-24T20:00"` | once, at that local date and time |
| `daily` | `time = "03:00"` | every day |
| `weekly` | `days = ["mon", "fri"]`, `time` | on those days |
| `interval` | `every` (seconds) | repeatedly, counted from the previous run (it continues across restarts of Gravekeeper) |
| `after-boot` | `delay` (seconds) | once per boot of the computer, however late Gravekeeper starts |

`action` is `start`, `stop` or `restart` (with `app`), or `run` (with `program`, optional `args`, `cwd`, and `timeout` in seconds, default 3600 — the program is killed if it runs longer).

**Time zones and DST.** Times are wall-clock times in `time_zone` (the system zone if absent). A time skipped by a DST change runs at the next valid instant; a time that occurs twice runs once, at the first occurrence.

**Missed runs.** A run counts as missed when it is more than 2 minutes late — because Gravekeeper was not running or the computer was asleep. With `missed = "skip"` it is recorded (a `schedule_missed` event) and the next regular run is awaited; with `missed = "run-once"` it runs once as soon as possible, however many runs were missed. The time of the last run is kept in the history database, so this also works across restarts. A `run` action that is still running when the next run is due is not started twice; that run is skipped and recorded.

## Webhooks

Each webhook receives an HTTP `POST` for the selected events. The `json` format sends:

```json
{"source": "gravekeeper", "host": "my-pc", "time": "2026-10-19T03:00:00Z",
 "level": "warning", "kind": "app_exited", "app": "Web server",
 "message": "exited with code 1 after 3m 12s"}
```

`slack` sends `{"text": "…"}` and `discord` sends `{"content": "…"}` with the same information on one line.

Events that can be sent: `app_started`, `app_stopped`, `app_exited` (unexpected exit), `app_start_failed`, `restart_scheduled`, `restart_gave_up`, `schedule_succeeded`, `schedule_failed`, `schedule_missed`, `resource_alert`, `resource_recovered`, `engine_started`, `engine_stopped`, `config_error`. The default selection is the problem events.

Delivery is retried up to 4 times (after 2, 4 and 8 seconds) on network errors, `5xx` and `429`; other answers fail immediately. A failure is recorded as a `webhook_failed` event, which is never itself sent to webhooks.

The URL and header values never appear in logs, events or the GUI (which shows only the host). They are stored in plain text in this file, which is readable only by you on Linux and macOS; moving them to the OS credential store is planned.

## Validation

The file is rejected as a whole if it:

- is not valid TOML, or contains unknown keys (typos are reported, not ignored)
- has no `schema_version`, or a newer one than this build understands
- has an application without a name or program, duplicate ids or names, an environment variable name that is empty or contains `=`, or a restart policy whose initial backoff is 0 or larger than the maximum
- has a schedule with an unknown time zone, no days (`weekly`), a zero interval, an empty program or zero timeout (`run`), or one that refers to an application that does not exist
- has a webhook whose URL does not start with `https://` or `http://`, an invalid header name, or an event that cannot be sent
- has a monitoring threshold above 100, a zero interval, or a zero log file size

When the file cannot be loaded, Gravekeeper starts with no applications, shows the error at the top of the window, and **does not write to the file** until it has been fixed and reloaded.

## Schema versions

`schema_version` is increased whenever the format changes incompatibly. Gravekeeper migrates older versions when loading them and refuses newer ones, so a downgrade cannot silently drop settings.

| Version | Changes |
|---|---|
| 1 | Applications and general settings |
| 2 | Monitoring, logging, schedules, webhooks; `boot_delay` for applications. Version 1 files are read as-is and written back as version 2 on the next save. |
